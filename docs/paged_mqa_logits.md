# paged_mqa_logits 算子说明与性能报告

`aiter.paged_mqa_logits` 面向分页 KV cache 的稀疏注意力索引阶段，计算 FP8 Query 与共享 Key 的加权 ReLU 分数。本报告比较 AITER 公开接口与固定版本的 **original 实现**；original 是本次性能测试的对照实现，不是 AITER 的旧 kernelId。

测试日期为 **2026-09-17**，文档整理日期为 **2026-09-18**。gfx936、gfx938 各测试 32 个 shape / 页布局组合，共 64 个 case。按 ±2% 持平区间，gfx936 的 Graph / eager 均为 32 项领先；gfx938 的 Graph 为 31 项领先、1 项持平，eager 为 32 项领先。完整数据和适用范围见下文。

## 算子功能

对每个请求的每个 Query，算子通过页表找到历史 Key，依次完成 QK 点积、ReLU、按 head 加权求和，输出用于候选 token 排序的分数。所有 head 共享同一份 Key；本接口不执行 softmax、Value 聚合或 TopK 选择，也不隐式乘以 `1/sqrt(D)`。

记：

| 符号 | 含义 |
|---|---|
| `B` | 请求数 / batch size |
| `R` | 每个请求的 Query 数，支持 1、2、4；多 Query 可用于 MTP 场景 |
| `H` | 当前 rank 的索引 head 数，支持 32、64 |
| `D` | 每个 head 的特征维度，固定为 128 |
| `N` | 输出候选列数，即 `max_model_len` |
| `P` | KV cache 中分配的物理页数 |
| `S` | 每页容纳的 Key 数，即 page size |
| `T` | 每个请求的页表容量，最多覆盖 `T*S` 个候选 |
| `L_b` | 请求 `b` 的有效上下文长度，即 `context_lens[b]` |

对于逻辑候选位置 `n`，物理页为 `p = block_tables[b, n // S]`，页内位置为 `j = n % S`。将 FP8 字节解码后的 Key 记为 `K[p,j,d]`，对应 FP32 反量化系数记为 `s[p,j]`，则：

```text
row = b * R + r
score[row, n] = sum_h weights[row, h] *
               ReLU(sum_d float(q[b, r, h, d]) * float(K[p, j, d]) * s[p, j])

有效区间：0 <= n < L_b - R + r + 1
输出形状：[B*R, N]，类型：FP32
```

例如 `R=2、L_b=100` 时，第 0 个 Query 可见 `[0,99)`，第 1 个 Query 可见 `[0,100)`。`weights` 可以为负数，因此最终分数也可以为负数。默认 `clean_logits=True`，有效区间以外的全部输出为 `-inf`，包括 `L_b` 之后的远端尾部。

## 接口与参数

```python
from aiter import paged_mqa_logits

logits = paged_mqa_logits(
    q,
    kv_cache,
    weights,
    context_lens,
    block_tables,
    max_model_len,
    out=None,
    clean_logits=True,
    kernelId=None,
)
```

`out`、`clean_logits`、`kernelId` 为仅限关键字参数。

| 参数 | 类型 / 形状 | 含义与约束 |
|---|---|---|
| `q` | `torch.float8_e4m3fn [B,R,H,128]` | 已量化的 Query；`B>0`、`B*R<=65535`、`R∈{1,2,4}`、`H∈{32,64}` |
| `kv_cache` | `torch.uint8 [P,S,1,132]` | 打包的 FP8 Key 与 FP32 scale；`P>0`、`P*S*132<=2**31-1`；实际字节布局见下一节 |
| `weights` | `torch.float32 [B*R,H]` | 每个 Query、每个 head 的权重；允许正数、负数和零 |
| `context_lens` | `torch.int32 [B]` | 每个请求的有效长度；调用方保证 `R<=L_b<=min(N,T*S)` |
| `block_tables` | `torch.int32 [B,T]` | 逻辑页到物理页的映射；`0<T<2**31`；所有被使用的物理页编号必须位于 `[0,P)` |
| `max_model_len` | Python `int` | 输出宽度 `N`；`0<N<2**31`，不接受 `bool` |
| `out` | 可选 `torch.float32 [B*R,N]` | 默认由接口分配；传入时复用并返回该张量，不得与任一输入共享底层 storage |
| `clean_logits` | Python `bool`，默认 `True` | 是否要求无效输出全部为 `-inf`；设为 `False` 时，由调用方负责尾部初始化或屏蔽，不能依赖所有 kernel 对无效位置的写入行为 |
| `kernelId` | 可选 Python `int` | 默认自动选择架构对应路径；显式可选值见架构支持表 |
| 返回值 | `torch.float32 [B*R,N]` | 第 `b*R+r` 行对应请求 `b` 的第 `r` 个 Query |

所有输入和 `out` 必须位于同一 GPU、连续存储且不需要梯度。Q 和 KV cache 的起始地址至少 4 字节对齐；通常由 `torch.empty` 等分配的张量也满足优化路径所需的 16 字节对齐。接口用于推理，不提供 autograd。

接口检查类型、形状、设备、连续性和输出别名等元数据。为避免热路径的主机同步，接口不会把 `context_lens`、`block_tables`、scale 内容拷回 CPU 逐项检查；调用方需要保证上述长度、页编号以及 **scale 为正的有限 FP32 数值** 等约束。共享页路径中的 GPU 一致性检查用于判断是否可以复用 Key，不能代替输入合法性检查。

### KV cache 的打包布局

`[P,S,1,132]` 是接口承载字节的张量形状。**每页先连续存放全部 `S*128` 个 Key 字节，再连续存放 `S` 个 FP32 scale；当 `S=64` 时，不是每个 token 的 128 个 Key 字节后紧跟 4 个 scale 字节。**

| 页大小 | 每页字节数 | Key 区间 | scale 区间 |
|---|---:|---|---|
| `S=1` | 132 | `[0,128)`，1 个 FP8 Key | `[128,132)`，1 个 FP32 scale |
| `S=64` | 8448 | `[0,8192)`，64 个 FP8 Key | `[8192,8448)`，64 个 FP32 scale |

页内第 `j` 个 Key 从字节偏移 `j*128` 开始，scale 从字节偏移 `S*128+j*4` 开始。不要通过 `kv_cache[p,j,0,:128]` 来读取 `S=64` 的逻辑 Key；应按每页原始字节区间解包。

### 架构与 kernelId 支持

| 架构 | 支持的 `S` | `kernelId=None` | 显式 kernelId | 验证范围 |
|---|---|---|---|---|
| gfx936 | 1、64 | ID6 / ID7 | 6、7 | 实卡功能与本报告的性能矩阵 |
| gfx938 | 1、64 | ID6 / ID7 | 0、1、2、3、6、7 | 实卡功能与本报告的性能矩阵；ID0–3 仅支持 `S=1` |
| gfx946 | 1 | ID4 | 4、5 | Perf Model 功能验证；无实卡性能结论 |

- **ID6**：独立请求的 HCU 分页计算路径，支持 `H=32/64`、`R=1/2/4`。
- **ID7**：`H=32、R=1` 的双请求 Key 复用路径，每次调用在 GPU 检查所用页编号及长度；不匹配的组、未配对的请求按独立请求计算。
- **自动选择**：满足 `H=32、R=1、B>=32、P*S<=2*N`，且 gfx936 的 `N>=4096` 或 gfx938 的 `N>=16384` 时选择 ID7；其余选择 ID6。页表仍会在 GPU 上检查，不会仅凭容量判定可共享。
- gfx938 的 **ID0–3** 保留为显式 Opus 路径；本报告的 AITER 性能列使用默认 ID6/7，不能将该性能结论套用到 ID0–3。
- gfx946 的 **ID4/5** 分别使用 K32 / K64 prefetch 路径。当前支持范围仍为 `S=1`，不支持直接运行本报告的 `S=64` 性能矩阵。

## 使用方式

### 构造 S=64 的分页输入并调用

以下示例适用于 gfx936 / gfx938。虽然 PyTorch API 使用 `cuda` 命名，在 ROCm / HCU 环境中仍使用相同名称。

```python
import torch
from aiter import paged_mqa_logits

device = torch.device("cuda:0")
B, R, H, D = 2, 1, 32, 128
S, N = 64, 256
T = (N + S - 1) // S
P = B * T  # 两个请求各自使用独立物理页

q = (torch.randn(B, R, H, D, device=device) * 0.25).to(
    torch.float8_e4m3fn
)
keys = (torch.randn(P, S, D, device=device) * 0.25).to(
    torch.float8_e4m3fn
)
scales = torch.ones(P, S, device=device, dtype=torch.float32)

# 按整页打包：先放所有 Key 字节，再放所有 FP32 scale 字节。
raw = torch.empty(P, S * (D + 4), device=device, dtype=torch.uint8)
raw[:, :S * D].copy_(keys.view(torch.uint8).reshape(P, S * D))
raw[:, S * D:].copy_(scales.view(torch.uint8).reshape(P, S * 4))
kv_cache = raw.view(P, S, 1, D + 4)

weights = torch.randn(B * R, H, device=device, dtype=torch.float32)
context_lens = torch.tensor([N, N - 13], device=device, dtype=torch.int32)
block_tables = torch.arange(P, device=device, dtype=torch.int32).reshape(B, T)

logits = paged_mqa_logits(
    q, kv_cache, weights, context_lens, block_tables, N
)
assert logits.shape == (B * R, N)
assert logits.dtype == torch.float32
# 第 2 个请求不足 N 的部分已被屏蔽为 -inf。
assert torch.isneginf(logits[1, N - 13:]).all().item()
```

生产调用通常不需要示例末尾的 `.item()` 检查，避免额外同步。使用 `R=2/4` 时，相应调整 `q` 与 `weights` 形状，并保持每个 `context_lens[b]>=R`；算子自动应用逐 Query 的可见长度。gfx946 可将示例的 `S` 改为 1，并重新按 `S` 计算 `T`、`P` 和打包布局。

### 复用输出与 Graph 回放

沿用上一段的输入，可通过预分配 `out` 减少重复输出分配。接口仍可能需要内部 scratch；预分配输出不表示整个调用零分配。

```python
out = torch.empty(B * R, N, device=device, dtype=torch.float32)


def run():
    return paged_mqa_logits(
        q, kv_cache, weights, context_lens, block_tables, N,
        out=out, clean_logits=True,
    )


# 首次调用可能触发 JIT；在 Graph 捕获前完成编译和预热。
run()
stream = torch.cuda.Stream(device=device)
stream.wait_stream(torch.cuda.current_stream(device))
with torch.cuda.stream(stream):
    for _ in range(5):
        run()
stream.synchronize()

graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(graph, stream=stream):
    run()

graph.replay()
torch.cuda.synchronize(device)
# 结果写入 out；后续可重复 graph.replay()。
```

算子在当前 stream 上执行，热路径不做主机同步。Graph 回放时需保留输入、输出的存储地址及形状；可原地更新内容，但仍需满足长度、页表和 scale 约束，并保证更新与回放的 stream 顺序。ID7 在每次回放中重新检查页表和长度，适用于原地变更元数据的情况。示例中的同步仅用于预热结束和读取最终结果。

### Shape 与数据分布

- 每个架构包含 **22 个模型典型 shape + 4 个 MTP shape + 6 个共享页 shape**。模型 shape 是合成的算子测试负载，不是线上请求回放。
- `H=32` 使用 GLM-5.1 的 rank-local 索引 head 数，不再按 TP 除以 head 数。`H=64` 使用已有 DeepSeek-V4-Flash C4 候选配置；这里的 `N` 是 C4 后的候选数，不是压缩前上下文长度，也不是 TopK 的 `k`。
- **独立页**共 26 项：`P=B*ceil(N/64)`，每个请求在自己的物理页区间内做无放回随机页映射，不同请求互不重叠。
- **共享页**共 6 项：`P=ceil(N/64)`，所有请求使用同一份随机排列页表。此组体现完全共享 Key 的复用收益，应与独立页分开理解。
- 性能输入的 `context_lens` 全为 `N`；`R=2` 时，第 0 个 Query 的最后一列按因果可见性屏蔽。更短上下文及远端尾部由功能测试另行覆盖。
- Q/K 由 `randn*0.25` 转为 FP8，性能输入中的非正规数统一在生成阶段置零；scale 取 `2**U(-2,2)`，weights 包含正数、负数及零。两种实现使用完全相同的输入张量。

**可比数值范围为 FP8 正规数与零。** gfx936 的 original 对 KV 中 FP8 非正规数存在清零行为，而 AITER 保留非正规数语义。因此本报告不能被解释为两种实现对所有 FP8 位模式都等价。AITER 的独立功能测试另外覆盖非正规数和有限极值，没有通过改变参考值或放宽误差来取得性能收益。

参考值直接读取实际量化字节，以 FP32 计算上述公式并关闭 TF32。验收逐元素满足 `abs(actual-reference)<=0.05+0.05*abs(reference)`，同时要求有效输出有限、所有无效位置均为 `-inf`。

- **采样**：7 轮 A→B / B→A 交替测试，逐实现取 7 个样本的中位数。表中单位为微秒（µs），保留三位小数。
- **eager**：用 GPU events 包围公开 API 调用循环，标准每轮 20 次。包含调用中产生的转换、清理、计算等 GPU 工作，也包含 GPU 时间线上等待主机校验、分配及发射所产生的空隙；它不是 Python 调用的 CPU wall time，也不是单个 kernel 耗时。
- **Graph**：一次捕获 20 次完整 API 调用，标准每轮回放 20 次，再除以 `20*20` 得到单次接口的 GPU 时间。内部转换、清理和计算均计入；回放不会重新执行 Python 校验或主机分配，因此不能称为逐次含主机分配开销。
- JIT 编译、输入生成、参考计算、Graph 捕获及预热不计入样本。没有在 API 外预先替 AITER 完成其内部必要的数据转换。
- 波动大于 5% 或接近 ±2% 持平区间的 case 延长为每轮 100 次调用 / 回放，仍取 7 轮中位数。使用整项复测结果替换原项，不挑选单轮最小值。
- gfx938 独立页 `B64/R1/H32/N32768` 采用每轮 100 次，并在每个 A/B 样本之前分别执行相同的 2000 ms GPU 预热。下表使用最终稳态结果：AITER Graph `233.514 µs`、original Graph `262.481 µs`。

### 性能指标定义

沿用报告模板的性能提升口径：

```text
单项加速比 = T_original / T_AITER
性能提升 (%) = (T_original - T_AITER) / T_AITER * 100
             = (单项加速比 - 1) * 100

组内几何平均加速比 = exp(mean(log(T_original / T_AITER)))
组内性能提升 (%) = (组内几何平均加速比 - 1) * 100
```

正值表示 AITER 更快；例如提升 `+25%` 表示加速比 `1.25x`，对应延迟降低 `20%`，两种百分比的分母不同。组内每个 case 等权，不按 batch 或候选长度加权，也不对百分比作算术平均。

“快 / 平 / 慢”按 `T_AITER/T_original` 判断：小于 `0.98` 为快，`[0.98,1.02]` 为平，大于 `1.02` 为慢。因此提升为小幅正值的 case 仍可能归为持平。CV 为 7 轮样本的标准差除以均值；下文“最大 CV”取组内两种实现的最大值。

## 优化路径与结果适用范围

gfx936 在大部分独立 S64 页路径中将 Key 直接加载到寄存器并精确转换为 FP16，减少整块 KV 转换缓冲的开销；小缓存或高复用缓存保留向量化预转换。gfx938 对 16 字节对齐的 S64 数据使用 MLS / DS Matrix 与原生 FP8 MMAC，并根据工作量选择不同候选 tile。共享页路径通过逐次检查的双请求 Key 复用减少重复读取。公开接口同时合并了默认分配路径的元数据检查和 native 调用。

这些优化的效果已包含在完整公开 API 的 Graph / eager 数据中。预分配 `out`、非默认 kernelId、S1 页、4 字节偏移视图等虽然有对应功能覆盖，但不应直接套用本报告的 S64 默认接口延迟。R=4 通过功能测试，本文性能矩阵仅含 R=1/2。

结果限定于所列设备、软件版本、输入分布和 shape；未测试 vLLM 端到端吞吐、其他数据类型、其他 head/page size 或 original 的额外 prefill / 调度元数据模式。gfx946 仅完成 Perf Model 功能验证，不能据此推导实卡性能。
