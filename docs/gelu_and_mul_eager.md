# GELU 与乘法融合算子的 eager 兼容路径

当参考实现对 FP16/BF16 输入分别执行 PyTorch eager 模式下的 GELU 和乘法时，
可以显式调用以下兼容接口：

```python
import torch
import torch.nn.functional as F
import aiter

inp = torch.randn(32, 5248, device="cuda", dtype=torch.bfloat16)
x, gate = inp.chunk(2, dim=-1)
out = torch.empty_like(x)
aiter.gelu_and_mul_eager(out, inp)
reference = F.gelu(x, approximate="none") * gate
```

`gelu_and_mul_eager(out, input)` 是新增接口，并未向 `gelu_and_mul` 增加参数。
现有接口仍保持仅在最终输出时舍入的行为。新接口与现有激活算子 API 一致，
将结果写入 `out`，返回 `None`。

## 数值行为

原融合 kernel 使用 FP32 计算 GELU 和门控乘法，仅在最终输出时舍入。
eager 路径先将 GELU 结果舍入到输入数据类型，再提升为 FP32 执行乘法，
最后再次舍入。兼容 kernel 在寄存器中复现这次中间类型转换，
无需分配临时张量，也无需第二次 kernel 启动。

兼容实现采用与 PyTorch `approximate="none"` GELU 相同的、基于 erf 的表达式，
不使用 tanh 近似。逐位一致性以测试环境中安装的 PyTorch 构建版本为基准，
不保证在任意设备数学库、编译器或 PyTorch 版本之间均成立。

对于非 NaN 结果，按原始 16 位表示逐位比较，包括带符号的零和无穷值。
对于 NaN，仅要求双方是否为 NaN 的判定一致，不约束 NaN 的载荷位和符号位。

### FP16 单行向量化的舍入边界

在本次验证的 PyTorch 2.11.0 / DTK 26.04 构建中，单行 `x` 连续，
输入地址满足 16 字节对齐时，PyTorch GELU 的完整向量化块包含
`256 × 8 = 2048` 个元素。该路径先形成 FP32 乘积，再转换为 FP16；
尾部、不满足此对齐条件或多行非连续 `x` 切片所走的路径，则允许编译器生成
`v_fma_mixlo_f16`，合并最后一次 FP32 乘法与 FP16 转换。
两者在少数舍入边界和负零上存在差异。例如，输入 `-1.4853515625`、门控值为 1 时，
完整向量化块输出 `-0.10205078125`，尾部或多行路径输出 `-0.10211181640625`。

兼容实现根据行数、输入对齐和列位置保留对应的舍入顺序，使用空汇编约束阻止编译器
跨分支合并转换；这些约束本身不生成设备指令。仍然只启动一个 kernel，
也不增加临时张量。仅添加 `-ffp-contract=off` 不能解决这一混合乘法/转换差异。
这里的 2048 元素边界来自已验证的 PyTorch 构建，不是硬件或 GELU 数学定义的保证；
升级 PyTorch 或 DTK 后应重新运行全编码、对齐和边界回归。

## 小行数调度

将输入前面的各维展平为 `rows`，输出最后一维宽度记为 `d`：

- `rows <= 64`：每 256 列一个 block，网格为 `[ceil(d / 256), rows]`，
  每线程计算一个元素，超出 `d` 的线程直接返回。
- `rows > 64`：一行一个 block，线程内循环处理多列。

以 `d=2624` 为例，1、4、8 行分别启动 11、44、88 个 block，每线程计算一个元素。
按列拆分将行内独立工作分配给更多 block，避免小行数时并行度不足和线程内循环过长。
调度由 `gelu_and_mul_eager(out, input)` 内部选择，调用方无需额外传入参数。

## 输入输出约束

- 输入：连续存储的 FP16 或 BF16 GPU 张量，形状为 `[..., 2 * d]`。
- 输出：连续存储的 GPU 张量，形状为 `[..., d]`，数据类型和设备与输入一致。
- 输入与输出的内存不得重叠。支持空张量。
- 支持奇数 `d`，也支持线程块未满的尾部处理；输入的最后一维仍须为偶数，
  因为该维度包含两个等长部分。
- 回归测试覆盖当前 HIP 流、计算图捕获与重放，以及 `torch.compile`。
  接口沿用现有面向推理的输出参数 API，不新增自动求导实现。

## 编译隔离

`module_activation_eager` 单独编译兼容路径的源码。
原有 `module_activation` 使用 `-fgpu-flush-denormals-to-zero`；
若兼容路径也使用该选项，便会丢失 eager 参考结果中的 BF16 次正规数。
当前 AITER JIT 的额外编译选项对整个模块生效，因此将兼容路径独立为模块，
可以单独配置其浮点行为，同时保持 SiLU、原有 GELU 和量化激活算子的编译行为。
若合并到同一模块并保留这种隔离，则需要增加按源文件设置编译选项的支持。

唯一新增的编译选项是 `-fno-gpu-flush-denormals-to-zero`。
实现没有将 `erf` 替换为其他设备数学库入口，也没有全局禁用浮点运算收缩
（例如将乘法和加法合并为 FMA）。

## 验证结果

以下结果对应 2026-10-16 验证的当前最终实现。
源码基线为 `a400373fa36b721a5f5a1815ac8d093ee71c9481` 加上本次修改。
两台服务器均使用容器 `zxw_vllm_0922`、PyTorch 2.11.0、
Torch HIP 6.3.26113、DTK 26.04 和 AICC/Clang 18.0.0。
实际设备分别为 bmz 上的 gfx936 和 TJ-yeleng-176.252 上的 gfx938，
均使用物理 GPU 0。验证使用独立的源码和 JIT 目录，未替换容器中预装的软件包。

两个架构均通过 **159/159 项回归**，包括 FP16/BF16 的全部 65,536 种输入编码、
14 个门控值、单行对齐与尾部、多行非连续 `x` 切片等用例。
非 NaN 结果与 eager 参考逐位一致，NaN 判定一致。
每台另外完成 **74 个形状/类型组合**的性能及输出检查，兼容实现的不一致数量均为零。
