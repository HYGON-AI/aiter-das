# HCU CustomAllreduce selective algorithm results (2026-10-10)

[返回最新用法与性能](../custom_allreduce.md)

gfx936：BW200 / UBB BW1000，80 CU；gfx938：BW1100，72 CU。测试使用TP2/TP4、单机IPC。
每行30样本，Graph每样本32次操作，取每次较慢rank。单位μs；RCCL包含clone。复制、RNE与同步保护均保留。
每架构1376组（含旧基线完整tile、Graph/eager、各dtype与后端）通过精度检查。所有样本保留。
标有 `*` 的Graph行CV>10%；表中只列BF16，完整FP16/BF16/FP32统计单独保存在测试数据归档中，不随源码分发。

本文是历史算法对照，采用当时的阈值。当前自动分派规则见[使用说明](../custom_allreduce.md)，最终性能见[组合结果](custom_allreduce_optimized_20261011.md)。
LL在TP2极小载荷有观测收益；gfx936 TP2 4KiB由14.115降至10.672μs（约24.4%），两行CV分别1.80%/2.56%。
LL128在TP2约64KiB有收益，但192/896KiB退化；gfx936 TP4 56/64KiB的新算法也慢于传统路径。
该历史结果不代表当前auto策略；显式ll/ll128不保证所有支持尺寸都有收益。
gfx938 auto时段有明显波动，且超出LL范围的相同传统kernel也变慢；这些数据不能单独证明算法变慢。
没有筛掉慢样本或反复重测挑最快结果。

## 使用边界

两阶段partial tile修复已由TP4交错Graph和实际trace确认；完整tile、优化尾部、naive尾部均有对应kernel记录。
旧baseline只运行合法完整tile，未用已知发散barrier的旧尾部代码做性能对照；不声称尾部修复的加速比。
TP2大载荷仍是传统one-stage；gfx938 8/32MiB的RCCL+clone较快，本次没有消除这一差距。
原始样本、失败、trace、构建记录和JSON汇总单独归档；汇总保留median/P95/max/CV及每组测试范围。
Fabric跨节点、gfx92a/其他架构和扩展rank硬件结果不能由本表外推。
